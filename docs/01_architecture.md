# Архитектура веб-сервиса

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Хостинг | Vercel (preview на каждый PR, production из `main`) | Требование проекта; нулевая настройка для Next.js |
| Репозиторий | GitHub, монорепо pnpm workspaces | Спецификация, ядро и интерфейс версионируются вместе |
| Фронтенд + API | Next.js (App Router) + TypeScript strict | Один язык для ядра и интерфейса |
| Расчётное ядро | `packages/engine` — чистый TypeScript без зависимостей от UI/БД, `decimal.js` для денег | Детерминированность, тестируемость, запуск в браузере (Web Worker) и на сервере |
| Спецификация | `packages/spec` — YAML из `data/` компилируется в типизированный JSON, схемы `zod` | Код не может сослаться на несуществующий параметр/источник — ошибка сборки |
| БД | Postgres (Neon через Vercel Marketplace) + Drizzle ORM | Проекты, версии расчётов, значения параметров, журнал изменений |
| Файлы | Vercel Blob | Вложения к параметрам уровня 4 (договоры, ГПЗУ, term sheet) |
| Авторизация | Auth.js | Автор изменений нужен для журнала и параметров уровня 5 |
| Экспорт | `exceljs` | Выгрузка результатов и паспорта источников в .xlsx для банка/инвестора |
| Графики | Recharts | Дашборд |
| Тесты | Vitest + Playwright | Юнит-тесты формул, золотые кейсы, e2e |
| CI | GitHub Actions | `validate_spec` → typecheck → tests → Vercel preview |

## Структура репозитория

```
/
├─ CLAUDE.md                  # правила для Claude Code
├─ data/                      # ЕДИНСТВЕННЫЙ источник правды (YAML)
│  ├─ sources.yaml
│  ├─ parameters.yaml
│  ├─ capex_items.yaml
│  ├─ regions.yaml
│  └─ formulas.yaml
├─ docs/                      # 00–02 пишутся руками, 03–05 генерируются из data/
├─ legacy/                    # исходный Excel и полная карта его ячеек
├─ tests/cases/               # золотые кейсы (входы + ожидаемые выходы)
├─ scripts/                   # validate_spec.py, render_docs.py, build_legacy_*.py
├─ packages/
│  ├─ spec/                   # загрузка и проверка YAML, генерация TS-типов
│  └─ engine/                 # расчёт: modules/time, tep, land, capex, sales, escrow, fin, tax, cf, kpi, checks
└─ apps/web/                  # Next.js: ввод, расчёт, паспорт показателя, дашборд, экспорт
```

## Расчётное ядро

- Вход: `ProjectInput` (значения параметров + ссылки на источники для project-параметров) и версия справочника (`spec_version`).
- Каждая формула из `formulas.yaml` — отдельная функция `F_<MODULE>_<NAME>(ctx)`, её ID совпадает с ID в YAML. Тест проверяет, что у каждой формулы в YAML есть реализация и наоборот.
- Порядок вычислений — топологическая сортировка по `depends_on`. Циклы запрещены (ставка ПФ берёт покрытие прошлого месяца).
- Выход: `ResultSet` — значения всех узлов + `trace` (для каждого узла: формула, входы, их значения). Из `trace` строится паспорт показателя.
- Никаких чисел в коде, кроме 0, 1 и математических констант. Линтер-правило + тест на поиск литералов в `packages/engine/src/modules`.

## Данные в БД

- `projects` — карточка проекта (регион, ОКТМО, кадастровый номер).
- `project_versions` — неизменяемые снимки входов + `spec_version` + результат (для воспроизводимости расчёта, показанного банку).
- `parameter_values` — значение, `source_id` или вложение, автор, дата, комментарий; для уровня 5 — обязательные поля `author`, `rationale`, `min`, `max`.
- `reference_snapshots` — версии справочника (`data/*.yaml`) с датой актуализации: ключевая ставка, прогноз МЭР, НЦС.
- `audit_log` — кто, что, когда изменил.

## Актуализация справочника

Ежеквартально (или по событию: решение ЦБ, новый прогноз МЭР, новые НЦС): обновить значения в `data/*.yaml`, дату `accessed`, прогнать `validate_spec.py`, открыть PR. Старые версии проектов продолжают ссылаться на свою `spec_version`.
