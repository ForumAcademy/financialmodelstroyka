# План реализации в Claude Code (GitHub + Vercel)

Каждый этап — отдельная ветка и PR с preview на Vercel. Промпт копируется в Claude Code как есть. Этап не начинается, пока не принят предыдущий.

## Этап 0. Репозиторий

1. Создать пустой репозиторий на GitHub, подключить к Vercel (Import Project).
2. Скопировать содержимое этого пакета в корень, закоммитить в `main`.
3. Промпт:

> Прочитай CLAUDE.md и docs/00–02. Настрой монорепо pnpm: packages/spec, packages/engine, apps/web (Next.js App Router, TypeScript strict). Добавь GitHub Actions: python scripts/validate_spec.py, pnpm typecheck, pnpm lint, pnpm test. Ничего не считай — только каркас.

**Приёмка:** CI зелёный, preview открывается.

Настройка Vercel (один раз, делает владелец репозитория): Add New → Project → Import `financialmodelstroyka`, Root Directory = `apps/web`, остальное по умолчанию. После этого Vercel сам создаёт preview для каждого PR.

## Этап 1. packages/spec

> Реализуй packages/spec: загрузка data/*.yaml, zod-схемы для sources, parameters, capex_items, regions, formulas; генерация TS-типов с union-типом всех ID параметров и формул. Сборка должна падать, если в коде используется несуществующий ID. Тест: все source_ids существуют, у level 1–3 есть URL.

**Приёмка:** опечатка в ID в коде — ошибка компиляции.

## Этап 2. Ядро: TIME, TEP, LAND

> Реализуй в packages/engine модули TIME, TEP, LAND строго по data/formulas.yaml (F.TIME.*, F.TEP.*, F.LAND.*). Одна формула — одна функция с тем же ID. Каждая функция пишет trace (входы, выход). Тесты: example из YAML + reconciliation_targets TEP из tests/cases/derbenevskaya_legacy.yaml.

**Приёмка:** площади кейса совпадают с исходником (143 560,388 м², 28 971,6 м², 35 294,59 м²); норматив машино-мест = 2 785.

## Этап 3. CAPEX

> Реализуй F.CAPEX.* и справочник capex_items.yaml: ставка × база × индекс, правила графика uniform / s_curve / at_milestone / follow_smr / follow_sales / manual. Проверки SCHEDULE_SUM и BUDGET_EQ_CF. Режим совместимости: ручные квартальные ряды из capex_legacy.

**Приёмка:** сумма весов = 1 для каждой статьи; УДС и «Прочие СМР» попадают в CF.

## Этап 4. SALES + ESCROW

> Реализуй F.SALES.* и F.ESC.*: ограничение продаж остатком, цена = рынок × стадия, структура оплат, эскроу по каждой очереди, раскрытие через TIME.ESCROW_RELEASE_LAG_M после РНВ. Режим совместимости: квартальный темп и +2%/кв из sales_legacy.

**Приёмка:** в режиме совместимости выручка по типам совпадает с reconciliation_targets (итого 118 130 288 024,50); в обычном режиме ПСН продано ≤ запаса.

## Этап 5. FIN

> Реализуй F.FIN.*: собственное участие вперёд, лимит, выборка, ставка с К1/К2 (покрытие за t−1), капитализация процентов, погашение из эскроу и ДКП, комиссии, эффективная ставка через XIRR. Траектория ключевой ставки — из FIN.KEY_RATE_PATH.

**Приёмка:** долг и проценты на конец = 0; нет циклических зависимостей; пример F.FIN.RATE даёт 0,1385.

## Этап 6. TAX + CF + KPI + CHECK

> Реализуй F.TAX.* (режим НДС по таблице TAX.VAT_REGIME, экономия по ДДУ по письму Минфина от 28.07.2026, перенос убытков), F.CF.*, F.KPI.* (XNPV, XIRR, LLCR, LTC/LTV, пиковый капитал), F.CHECK.ALL. Любая неуспешная проверка блокирует отчёт и показывается на дашборде.

**Приёмка:** все пункты expected_differences_after_fix выполнены.

Этапы 1–6 завершают расчётное ядро. Дальше — сервис из двух разделов (docs/01, «Структура сервиса»): «Проекты» и «Справочник». Порядок: проекты → экраны проекта → справочник (чтение) → версии справочника → бенчмарки → роли → экспорт → сценарии → сравнение версий.

## Этап 7. Проекты и главный экран

> Подключи Postgres (Neon через Vercel Marketplace) + Drizzle и вход по общему паролю (docs/01, «Доступ к сервису»). Таблицы по docs/01: users, projects, project_versions (с reference_version_id и kpi_summary), parameter_values, sources, attachments, reference_versions (одна запись — версия 1 из data/*.yaml), audit_log. Главная страница — список проектов: название, регион, класс, площадь участка, выручка, NPV, IRR акционера, маржа, статус, дата изменения, автор; поиск, фильтры (регион, статус, класс), сортировка по любому столбцу. Мастер «Создать проект», шаг 1: название, регион, кадастровый номер, класс, стадия; региональные параметры — из текущей версии справочника, пустые — обязательный ручной ввод. Действия: открыть, переименовать, скопировать, архивировать / вернуть; удаления нет. Сравнение 2–3 проектов. Сид: tests/cases/derbenevskaya_legacy.yaml → демо-проект «Дербеневская (демо)». Страница проекта — дашборд с ключевыми показателями из ядра.

Перед этапом владелец добавляет в Vercel переменные `APP_PASSWORD` и `APP_SESSION_SECRET` (инструкция — в PR этапа).

**Приёмка:**
- на главном экране можно создать, скопировать, открыть и архивировать проект; удалить нельзя, архивный проект открывается и копируется;
- показатели в списке совпадают с дашбордом проекта (тест: kpi_summary = ResultSet той же версии);
- каждая версия проекта хранит reference_version_id;
- все действия пишутся в audit_log с именем автора; без пароля ни одна страница и API недоступны;
- демо-проект открывается.

## Этап 8. Экраны проекта, проектные источники и паспорт показателя

> Сделай в разделе «Проекты»: (1) мастер ввода по разделам: общее, участок, ТЭП, вехи по очередям, бюджет, продажи, финансирование — с подсказками how_to_fill и выбором источника; (2) проектные источники внутри проекта (sources.scope = project): ГПЗУ, ППТ, ТЭП архитектора, договор на участок, term sheet банка, выборка аналогов, экспертные оценки — вложение в Vercel Blob, автор, дата; для уровня 5 — обязательные автор, обоснование, диапазон; (3) вкладки Исходные данные, ТЭП, Бюджет, План продаж, Эскроу, Финансирование, Налоги, CF (месяц / квартал / год), Дашборд; (4) по клику на любое число — паспорт показателя: формула словами и через ID, rationale, rejected, дерево зависимостей, общие источники со ссылками, проектные источники со вложениями; (5) результаты F.CHECK.ALL на дашборде.

**Приёмка:**
- из любой цифры дашборда за 2 клика видна ссылка на закон / статистику / документ;
- проектный источник виден только внутри своего проекта и не появляется в Справочнике и в других проектах (кроме копий проекта);
- параметр уровня 5 нельзя сохранить без автора, обоснования и диапазона;
- статусы «Утверждён» и «Архив» — только чтение.

## Этап 9. Справочник: методика, нормативы, источники (чтение)

> Сделай раздел «Справочник» (только чтение): Методика — все формулы из formulas.yaml (выражение, rationale, rejected, источники, пример, значение за прошлый месяц), поиск по ID и названию; Нормативы и ставки — параметры scope = template и scope = region (по субъектам из regions.yaml), с источниками и статусом проверки; Источники — реестр общих источников (scope = global) с кликабельными ссылками, датой проверки, отметкой «не сверен» и списком параметров и формул, которые на них ссылаются. Паспорт показателя в проекте ведёт на формулу и источник в Справочнике той версии, на которой посчитан проект.

**Приёмка:**
- все формулы, параметры и общие источники справочника доступны в интерфейсе, числа совпадают с data/*.yaml;
- у каждого общего источника уровня 1–3 ссылка кликабельна;
- из паспорта показателя переход на формулу и источник в Справочнике — одним кликом;
- проектные источники в Справочнике не показываются.

## Этап 10. Версии справочника и уведомления об изменениях

> Реализуй версии справочника по docs/01 («Справочник и его версии»): черновик версии, правки нормативов, текстов методики и общих источников с обоснованием и источником, проверки перед публикацией (packages/spec/src/checks.ts), публикация, пробный пересчёт затронутых проектов и сохранение влияния на NPV / IRR / маржу, выгрузка опубликованной версии в data/*.yaml автоматическим PR. В проекте: уведомление «Доступна новая версия справочника» со списком изменений и влиянием; кнопка «Пересчитать» создаёт новую версию проекта; для утверждённого проекта — отдельное подтверждение. Вкладка «Версии» проекта — список версий с версией справочника каждой.

**Приёмка:**
- публикация новой версии справочника не меняет ни одной существующей версии проекта (тест: kpi_summary всех проектов до и после публикации совпадают);
- затронутый проект показывает уведомление со списком изменений и разницей NPV / IRR / маржи; незатронутый — не показывает;
- «Пересчитать» создаёт новую версию проекта, старая доступна и воспроизводится с тем же результатом;
- утверждённый проект без подтверждения не пересчитывается; после пересчёта — статус «В работе»;
- версию справочника с ошибкой проверки опубликовать нельзя.

## Этап 11. Бенчмарки: расценки компании и аналоги рынка

> Реализуй формулы F.BENCH.* строго по data/formulas.yaml с параметрами BENCH.* (docs/00, раздел 9). Таблицы company_benchmarks и market_comps, ввод в Справочнике с документом или ссылкой. В проекте: выборка аналогов (BENCH.MARKET_SAMPLE) с корректировками (BENCH.PRICE_ADJUSTMENTS) → стартовая цена и темп продаж (уровень 3); выборка расценок (BENCH.COST_SAMPLE) → ставка статьи бюджета (уровень 4). Статистика F.BENCH.STATS с предупреждениями; ручное исключение аналога с причиной — в журнал. Выборка замораживается в версии проекта; в паспорте показателя — аналоги, веса и корректировки. Изменения базы бенчмарков публикуются версией справочника.

**Приёмка:**
- на тестовой выборке из 3, 5 и 7 аналогов выбирается правильный метод: 3 — средневзвешенная по близости, 5 и 7 — медиана; при 2 аналогах — ошибка без экспертного обоснования;
- данные раньше 01.07.2024 (последней даты BENCH.STRUCTURAL_BREAK_DATES) и старше окна не попадают в расчёт; при менее чем 5 аналогах в окне 6 месяцев окно расширяется до 12;
- выброс подсвечивается, но остаётся в выборке, пока его не исключат вручную с причиной; исключение видно в журнале;
- медиана, квартили и коэффициент вариации совпадают с PERCENTILE.INC / QUARTILE.INC / STDEV.S в Excel на тестовом наборе;
- параметр со ссылкой на выборку показан как уровень 3 (аналоги) или 4 (расценки), в паспорте видны состав выборки, веса и корректировки;
- пополнение базы бенчмарков не меняет уже посчитанные версии проектов;
- у каждого параметра BENCH.* есть source_ids и basis; validate_spec.py — 0 ошибок.

## Этап 12. Роли, права, журнал изменений

> Личный пароль без логина (docs/01, «Доступ к сервису»: пароль генерирует сервис, по нему определяются пользователь и роль; хранится отпечаток HMAC с секретом `APP_PASSWORD_PEPPER`; защита от подбора) и роли администратор (методолог) / аналитик / наблюдатель по таблице docs/01 («Роли и права»); проверка прав на сервере. Заявки аналитиков на изменение Справочника (change_requests): подача с обоснованием и источником, рассмотрение методологом, принятая заявка — в черновик следующей версии. Журнал изменений Справочника: кто, что, когда, обоснование, затронутые проекты; фильтры по сущности и автору. Управление пользователями — у администратора.

**Приёмка:**
- аналитик не может изменить Справочник и чужой проект ни через интерфейс, ни через API (тест на каждый маршрут);
- по паролю однозначно определяется пользователь; перевыпущенный или отключённый пароль не работает; общий пароль отменён;
- наблюдатель может только смотреть и выгружать Excel;
- изменение Справочника без обоснования и источника не сохраняется;
- заявка проходит путь «подана → принята → в опубликованной версии» или «отклонена с комментарием», всё видно в журнале.

## Перед первым боевым расчётом закрыть

Список формирует `python scripts/validate_spec.py` (раздел WARN). Ключевые:

- режим НДС по ПСН/машино-местам в ДДУ и ДКП — подтвердить с налоговым консультантом;
- налог на прибыль застройщика (экономия по ДДУ): подтвердить распределение затрат по очередям;
- формула и коэффициенты платы за ВРИ (Москва, 593-ПП) — выписать из текста акта;
- Кпер НЦС для нужных регионов — из таблицы 1 НЦС 81-02-01-2026;
- ставки земельного налога — по ОКТМО через сервис ФНС;
- пояснить у автора исходника: ТЭПы!C35 (149 281 м²) и ТЭПы!C49 (5 200).
