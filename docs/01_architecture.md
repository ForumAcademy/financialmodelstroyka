# Архитектура веб-сервиса

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Хостинг | Vercel (preview на каждый PR, production из `main`) | Требование проекта; нулевая настройка для Next.js |
| Репозиторий | GitHub, монорепо pnpm workspaces | Спецификация, ядро и интерфейс версионируются вместе |
| Фронтенд + API | Next.js (App Router) + TypeScript strict | Один язык для ядра и интерфейса |
| Расчётное ядро | `packages/engine` — чистый TypeScript без зависимостей от UI/БД, `decimal.js` для денег | Детерминированность, тестируемость, запуск в браузере (Web Worker) и на сервере |
| Спецификация | `packages/spec` — YAML из `data/` компилируется в типизированный JSON, схемы `zod` | Код не может сослаться на несуществующий параметр/источник — ошибка сборки |
| БД | Postgres (Neon через Vercel Marketplace) + Drizzle ORM | Проекты, версии расчётов, значения параметров, журнал изменений |
| Файлы | Vercel Blob | Вложения к параметрам уровня 4 (договоры, ГПЗУ, term sheet) |
| Авторизация | Auth.js | Автор изменений нужен для журнала и параметров уровня 5 |
| Экспорт | `exceljs` в `packages/export` | Выгрузка проекта в .xlsx с живыми формулами и листом «Источники» для банка/инвестора |
| Графики | Recharts | Дашборд |
| Тесты | Vitest + Playwright | Юнит-тесты формул, золотые кейсы, e2e |
| CI | GitHub Actions | `validate_spec` → typecheck → tests → Vercel preview |

## Структура репозитория

```
/
├─ CLAUDE.md                  # правила для Claude Code
├─ data/                      # ЕДИНСТВЕННЫЙ источник правды (YAML)
│  ├─ sources.yaml
│  ├─ parameters.yaml
│  ├─ capex_items.yaml
│  ├─ regions.yaml
│  └─ formulas.yaml
├─ docs/                      # 00–02 пишутся руками, 03–05 генерируются из data/
├─ legacy/                    # исходный Excel и полная карта его ячеек
├─ tests/cases/               # золотые кейсы (входы + ожидаемые выходы)
├─ scripts/                   # validate_spec.py, render_docs.py, build_legacy_*.py
├─ packages/
│  ├─ spec/                   # загрузка и проверка YAML, генерация TS-типов
│  ├─ engine/                 # расчёт: modules/time, tep, land, capex, sales, escrow, fin, tax, cf, kpi, checks
│  └─ export/                 # выгрузка проекта в .xlsx (exceljs), без зависимостей от UI/БД
└─ apps/web/                  # Next.js: список проектов, ввод, расчёт, паспорт показателя, дашборд, экспорт
```

## Расчётное ядро

- Вход: `ProjectInput` (значения параметров + ссылки на источники для project-параметров) и версия справочника (`spec_version`).
- Каждая формула из `formulas.yaml` — отдельная функция `F_<MODULE>_<NAME>(ctx)`, её ID совпадает с ID в YAML. Тест проверяет, что у каждой формулы в YAML есть реализация и наоборот.
- Порядок вычислений — топологическая сортировка по `depends_on`. Циклы запрещены (ставка ПФ берёт покрытие прошлого месяца).
- Выход: `ResultSet` — значения всех узлов + `trace` (для каждого узла: формула, входы, их значения). Из `trace` строится паспорт показателя.
- Никаких чисел в коде, кроме 0, 1 и математических констант. Линтер-правило + тест на поиск литералов в `packages/engine/src/modules`.

## Данные в БД

Сервис многопроектный: у каждого ЖК своя финансовая модель. Расчёт всегда воспроизводим по неизменяемому снимку (`project_versions`).

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Пользователи (Auth.js) | `id`, `name`, `email` |
| `projects` | Карточка проекта (ЖК) | `id` (uuid), `name`, `region_code` (из `data/regions.yaml`), `oktmo`, `cadastral_number`, `housing_class` (enum из `GEN.HOUSING_CLASS`), `status`, `copied_from_project_id` (null или исходный проект), `current_version_id`, `created_by`, `created_at`, `updated_by`, `updated_at`, `deleted_at` |
| `project_versions` | Неизменяемый снимок расчёта | `id`, `project_id`, `number` (1, 2, …), `label`, `scenario`, `inputs` (jsonb, снимок `ProjectInput`), `spec_version` (хеш/дата `data/*.yaml`), `result` (jsonb `ResultSet` или ссылка на Blob при большом объёме), `kpi_summary` (jsonb: выручка, NPV, IRR акционера, маржа, пиковый капитал, LLCR, статус F.CHECK.ALL), `checks_passed` (bool), `created_by`, `created_at` |
| `parameter_values` | Текущие (рабочие) значения параметров проекта | `project_id`, `param_id` (ID из `parameters.yaml`), `value` (jsonb), `source_id` или `attachment_id`, `author`, `rationale`, `min`, `max` (для уровня 5 обязательны `author`, `rationale`, `min`, `max`), `updated_by`, `updated_at` |
| `attachments` | Вложения уровня 4 (Vercel Blob) | `id`, `project_id`, `blob_url`, `file_name`, `uploaded_by`, `uploaded_at` |
| `reference_snapshots` | Версии справочника (`data/*.yaml`) | `spec_version`, `actualized_at` (ключевая ставка, прогноз МЭР, НЦС), `content_hash` |
| `audit_log` | Журнал: кто, что, когда | `project_id`, `user_id`, `action` (create / rename / copy / status / param_change / calculate / export / delete), `payload` (jsonb: было → стало), `at` |

Регион проекта — это код из `data/regions.yaml`. Региональные параметры при создании проекта подставляются из справочника; если поле региона `null` (статус `structure_only` / `to_fill`), параметр становится обязательным для ручного ввода с документом (`needs_verification`), см. CLAUDE.md п. 8.

### Статусы проекта

| Статус | Код | Что можно делать |
|---|---|---|
| Черновик | `draft` | Всё: ввод, расчёт, переименование, удаление |
| В работе | `in_progress` | Ввод и расчёт; удаление запрещено (только архив) |
| Утверждён | `approved` | Только чтение. Утверждается конкретная версия (`current_version_id`); чтобы изменить — вернуть в «В работе» (фиксируется в журнале) или скопировать проект |
| Архив | `archived` | Только чтение, скрыт из списка по умолчанию (фильтр «Архив»); можно вернуть из архива в прежний статус или удалить |

Переходы: `draft → in_progress → approved`, любой → `archived`, `archived →` прежний статус, `approved → in_progress`. Каждый переход пишется в `audit_log`. Правила «кто может утверждать» — открытый вопрос (см. ниже).

### Операции с проектом

- **Создать** — мастер, шаг 1: название, регион (`GEN.REGION_CODE`), кадастровый номер (`GEN.CADASTRAL_NUMBER`), класс (`GEN.HOUSING_CLASS`). Создаётся `projects` в статусе `draft` и `parameter_values` с региональными значениями из `regions.yaml` (с их `source_ids`).
- **Переименовать** — меняет `projects.name` (= `GEN.PROJECT_NAME`), запись в журнал.
- **Скопировать** — новый проект (`draft`, `copied_from_project_id` = исходный, имя «<имя> (копия)»): копируются все `parameter_values` с источниками и ссылками на те же вложения; версии и журнал не копируются. Используется для вариантов концепции.
- **Архивировать / вернуть из архива** — смена статуса.
- **Удалить** — только из статусов `draft` и `archived`, после подтверждения вводом названия проекта. Мягкое удаление (`deleted_at`); данные физически удаляются через 30 дней.
- **Сравнить** — 2–3 проекта: `kpi_summary` их текущих версий на одном экране + ключевые входы (регион, класс, площадь участка, продаваемая площадь).

### Список проектов

Главная страница `/` — таблица/карточки: название, регион, класс, площадь участка (`LAND.AREA`), выручка (`F.SALES.REVENUE_TOTAL`), NPV (`F.KPI.NPV`), IRR акционера (`F.KPI.IRR`), маржа (`F.KPI.MARGIN`), статус, дата изменения, автор. Показатели берутся **только** из `project_versions.kpi_summary` текущей версии — того же `ResultSet`, что и дашборд проекта, поэтому числа совпадают. Если входы изменены после последнего расчёта, в строке показывается «пересчитать». Поиск по названию/кадастровому номеру, фильтры (регион, статус, класс), сортировка по любому столбцу (на сервере, SQL).

Демо-проект: `tests/cases/derbenevskaya_legacy.yaml` загружается сид-скриптом как проект «Дербеневская (демо)» в режиме совместимости.

## Экспорт в Excel

Модуль `packages/export` — чистый TypeScript на `exceljs`, на входе `ProjectInput` + `ResultSet` + реестры `packages/spec`, на выходе буфер .xlsx. Вызывается из API-маршрута `apps/web` (`GET /api/projects/:id/export?version=`), кнопка «Скачать в Excel» — на странице проекта и в строке списка.

Имя файла: `<Название ЖК>_финмодель_<ГГГГ-ММ-ДД>.xlsx` (символы, недопустимые в именах файлов, заменяются на `_`).

| # | Лист | Содержание |
|---|---|---|
| 1 | Обложка | Проект, дата расчёта, номер версии, `spec_version`, сценарий, автор, статус F.CHECK.ALL |
| 2 | Исходные данные | Каждый параметр: ID, название, значение, единица, источник, уровень, ссылка (гиперссылка), дата проверки, обоснование; для уровня 5 — автор и диапазон |
| 3 | Источники | Реестр источников, использованных в проекте, с кликабельными гиперссылками |
| 4 | ТЭП | F.TEP.* |
| 5 | Бюджет | Статьи: ставка × база × индекс = сумма (живая формула) |
| 6 | План продаж | По продуктам и очередям |
| 7 | Эскроу | По очередям |
| 8 | Финансирование | Выборка, ставка, проценты, погашение, остаток долга |
| 9 | Налоги | НДС, налог на прибыль, земельный налог |
| 10 | CF (мес) | Помесячно |
| 11 | CF (кв) | Агрегат по кварталам: `SUMIFS` по листу «CF (мес)» |
| 12 | CF (год) | Агрегат по годам: `SUMIFS` по листу «CF (мес)» |
| 13 | Дашборд | Ключевые показатели + графики |
| 14 | Проверки | Результат F.CHECK.ALL: проверка, результат, значение, допуск |

Правила листов:

- **Живые формулы** там, где Excel может воспроизвести расчёт: итоги и суммы (`SUM`), ставка × база × индекс, остатки (`предыдущий + приход − расход`), агрегаты CF по кварталам и годам, ссылки между листами. Показатели, требующие итераций или функций, которых нет в Excel в той же постановке (ставка ПФ с К1/К2, XIRR по месяцам), пишутся значением, рядом — ID формулы и пометка «значение из сервиса». Каждая ячейка с формулой содержит и кэшированный результат из `ResultSet`, чтобы файл сразу открывался с числами.
- **Рядом с каждой строкой** — столбцы «ID формулы» и «Описание» (`name` и `expr` из `formulas.yaml`).
- **Оформление**: ввод — синий шрифт, формулы — чёрный, ссылки на другие листы — зелёный; закреплённые шапки; формат `# ##0 ₽` для рублей, `0,00%` для долей, `ДД.ММ.ГГГГ` для дат; даты — настоящие даты Excel; форматирование только в используемом диапазоне (никаких столбцов до XFD).
- **Графики** на листе «Дашборд»: `exceljs` не создаёт диаграммы, поэтому данные графиков лежат таблицами на листе, а сами диаграммы добавляются в файл постобработкой (DrawingML-диаграммы Excel, связанные с этими таблицами), чтобы они оставались «живыми».

Проверка совпадения (тест `packages/export`): для демо-проекта и синтетического кейса (1) каждая ячейка-итог содержит кэш, равный `ResultSet` до 1 руб.; (2) файл пересчитывается LibreOffice в headless-режиме (в CI), и пересчитанные итоги (выручка, бюджет, CF, долг на конец) совпадают с сервисом до 1 руб.; (3) все гиперссылки листа «Источники» — `http(s)://`; (4) ни на одном листе нет ошибок `#REF!`, `#VALUE!`, `#DIV/0!`, `#NAME?`.

Импорт «Загрузить из Excel» — отдельный этап, только по запросу владельца продукта.

### Открытые вопросы (решает владелец продукта)

1. Кто может переводить проект в «Утверждён» и возвращать из него: любой пользователь или отдельная роль?
2. Вход в сервис (Auth.js): по ссылке на e-mail, через корпоративный аккаунт (Google/Microsoft/Яндекс) или по логину и паролю? Все пользователи видят все проекты?
3. Удаление: устраивает ли мягкое удаление с очисткой через 30 дней?

## Актуализация справочника

Ежеквартально (или по событию: решение ЦБ, новый прогноз МЭР, новые НЦС): обновить значения в `data/*.yaml`, дату `accessed`, прогнать `validate_spec.py`, открыть PR. Старые версии проектов продолжают ссылаться на свою `spec_version`.
